# Handoff: оптимизация FOC ADC ISR на F405 (MK5), 2026-11-14

Документ для следующего исполнителя. Содержит: что измерено, куда уходит
время ISR, оценку трёх последних коммитов, подробное описание методики
(включая PC-профиль), план дальнейших оптимизаций, отдельный раздел про
промахи кэша флеша и открытые вопросы.

Базовый коммит: `8fa1e5b` (HEAD ветки `main` на момент работы).
Артефакты сессии: `/home/okhsunrog/tmp_zfs/codex_tmp/oxifoc-isr-review.dW5aab/`
(ниже — `$D`). Предыдущая история замеров — в
[foc-loop-research.md](foc-loop-research.md); этот документ её не повторяет.

## 1. Главное

1. ISR занимает около 46.3 µs при периоде 66.66 µs (15 кГц). Одной горячей
   точки нет: это ~7900 тактов, размазанных по ~3900 различным инструкциям
   и ~16 КБ кода.
2. Три последних коммита (`4ae27e1`, `20f9eab`, `8fa1e5b`) дали около
   −0.5 µs за счёт исходников и ещё −0.8 µs за счёт `incremental = false`.
   Направление «убирать блокировки и барьеры» почти исчерпано: все
   критические секции в ISR стоят ~0.5 µs, все DMB — ~0.1 µs.
3. Время уходит в объём работы за цикл и в особенности флеша F405:
   - оценка фазы (Hall + наблюдатель + blend) — 16 µs;
   - «обвязка» вокруг контура тока (команды, защиты, телеметрия) — ~18 µs;
   - сам контур тока — ~11.6 µs;
   - из всего этого ~7 µs (15%) — промахи кэша флеша на переходах и
     литералах, ~2.3 µs — деления и корни.
4. Пробный патч на 12 строк (деления на константы → умножения) дал
   −0.86 µs на плате. Это больше, чем исходные правки трёх коммитов вместе,
   и совпало с прогнозом по профилю (~1.0 µs).
5. Реалистичная цель при умеренной переработке — 35–36 µs вместо 46.
6. Найден вероятный источник редких выбросов 88–94 µs: логирование
   `warn!` внутри ISR на входе в failsafe (раздел 9).

## 5. Оценка последних коммитов

**`4ae27e1` — АЦП-хэндлы принадлежат ISR.** Хороший и простой: убраны три
критические секции, `RefCell` и проверки `Option` на цикл; −0.5 µs по
вашим замерам. `static mut` внутри `#[interrupt]` — штатный безопасный
приём cortex-m-rt.

**`20f9eab` — драйвер принадлежит ISR.** По скорости нейтрален
(46.26 µs до него, 46.27 µs после `8fa1e5b`). ADC IRQ имеет приоритет 0,
поэтому прежняя внешняя секция никого не задерживала. Польза структурная:
задача больше не может захватить драйвер; раньше retime выполнялся из задачи
под PRIMASK вместе с `retime_stopped` и busy-wait ≥10 µs. Цена — модуль
`detection_timing` (~90 строк, только MK5) с атомарным автоматом из пяти
состояний и два async-метода в `DetectionBackend`. Ошибок в протоколе не
найдено. Проверенные случаи:

- таймаут `wait` в состоянии `AWAITING_SAMPLE` возвращает «Busy», хотя TIM1
  уже перенастроен; это закрывает цикл восстановления в
  `oxifoc-core/src/runtime/detect.rs:188`;
- пока задача не забрала `APPLIED`/`REJECTED` (до 1 мс), ISR каждый цикл
  заходит в `service` и ничего не делает — безвредно;
- `Drop` запроса сбрасывает слово в `IDLE` безусловно — согласовано с
  повторной подачей при восстановлении.

**Решение по откату: не откатывать.** `git revert 20f9eab` даёт два
конфликта в `oxifoc-f405/src/control/foc.rs` (тот же модуль правит
`8fa1e5b`), потребовалась бы повторная проверка детекции на плате, а
выигрыша по скорости нет. Если сложность мешает — упрощать канал: провести
retime обычной командой через `CMD_CHANNEL` с сигналом завершения по образцу
`COMMISSIONING_DONE`. Насколько это ложится на трейт `PhasePwm`, не
проверялось.

**`8fa1e5b` — «восстановление» времени.** Ценная часть — `incremental =
false` в release-профиле (−0.8 µs); по сути это исправление конфигурации.
Слияние флага и значения VBUS в одно слово с sentinel — аккуратно, API стал
чище (`measured_vbus_mv() -> Option<u32>`). Но выигрыши 0.1–0.2 µs,
приписанные одиночной загрузке и убранному барьеру, лежат на уровне шума
раскладки: один DMB стоит около одного такта.

**Замечание по методике предыдущих замеров.** Разницы меньше ~0.2 µs между
двумя перелинкованными образами нельзя приписывать правке исходников:
сдвиг адресов сам двигает время на ±0.2–0.5 µs (это видно и в ваших
экспериментах с версией `cortex-m`). Приём с заменой инструкций на NOP без
сдвига адресов — правильный. Для выбора направлений полезнее PC-профиль:
он даёт прогноз в тактах, который затем подтверждается одним A/B.

### 6.2 Сборка образов

Скрипт `$D/build2.sh` (расширение `build.sh` из прошлых сессий):

```sh
sh $D/build2.sh $D <корень-исходников> <метка> <доп-фичи> [доп-rustflags]
```

Суть:

```sh
cd "$root/oxifoc-f405"
[ -n "$flags" ] && export RUSTFLAGS="-C target-feature=+vfp2,-fp64 $flags"
DEFMT_LOG=warn CARGO_PROFILE_RELEASE_INCREMENTAL=false TMPDIR="$d" \
  cargo build --release --locked --target-dir "$d/target-$label" \
  --config "build.build-dir=\"$d/target-$label/build\"" \
  --no-default-features --bin oxifoc-f405 \
  --features "transport-spi,board-vesc6-mk5,task-priority,ccm-telemetry,bench-calibrated-clock${features:+,$features}"
```

- Пустой список доп-фич — production-образ, эквивалент `just build-mk5-spi`.
- `bench-foc-distribution` — «minimal»-диагностика: два чтения DWT на ISR и
  гистограммы в ОЗУ.
- Переменная `RUSTFLAGS` полностью заменяет `rustflags` из
  `.cargo/config.toml`, поэтому `+vfp2,-fp64` нужно повторять.
- Отдельный target-каталог на метку: сборки не влияют друг на друга, их
  можно запускать параллельно (но не во время прогона на плате).
- Правки исходников делались в `git worktree add --detach $D/wt HEAD`,
  чтобы основное дерево оставалось чистым; после — `git worktree remove`.

Собранные образы: `base-minimal`, `base-release`, `xo-minimal`,
`nojt-minimal`, `arith-minimal` (ELF, логи сборки и дизассемблеры в `$D`).

### 6.4 Среднее и распределение времени ISR

Скрипт `$D/run.py` (повторно использует функции из `previous-ab.py`
прошлых сессий):

```sh
uv run --no-project python -B $D/run.py base-minimal xo-minimal arith-minimal base-minimal:1
```

Аргумент — `<каталог-образа>[:<номер-блока>]`; диагностика берётся из
суффикса имени (`-minimal`). Для каждого образа:

1. `just cli-bridge status`: мотор Stopped, ошибок нет.
2. `probe-rs download --connect-under-reset --verify` и `probe-rs reset`.
3. Проверки: источник фазы `HallToObserver`, VBUS 23–25 В, FET < 50 °C.
4. `f405_timing.snapshot(15000)`: чтение RCC/TIM1/ADC и проверка контракта
   (ARR, CCR4, триггер, ранги, время выборки, dead time); `FLASH_ACR`.
5. Для точек +120 и +450: до пяти попыток, пока не наберётся два принятых
   прогона:
   - запись `1` в `FOC_DISTRIBUTION_CONTROL` по SWD (чтение должно вернуть
     `2` — взведено);
   - манёвр `just test-bridge <capture.parquet> <plan.json>`: velocity на
     t=0.3 с, stop на t=4.3 с, хвост 0.4 с, запись на 15 кГц;
   - `stop`, проверка что слово управления равно `3` (заморожено);
   - чтение 528 слов `FOC_DISTRIBUTION_DATA` и
     `bench_foc_profile.decode` → среднее, максимум, перцентили, превышения
     бюджета, интервалы между входами;
   - прогон принимается, если запись без потерь, все команды подтверждены и
     в логе нет `CommTimeout raised`.
6. В `finally`: stop, прошивка образа из `$D/initial-elf`, reset, статус.

Гистограммы пишет сама прошивка (бины по 64 такта ≈ 0.381 µs, только циклы
с активным мостом); во время манёвра по SWD ничего не читается. Сводка —
`python3 $D/summary.py`.

### 6.5 PC-профиль

**Принцип.** Регистр `DWT_PCSR` (`0xE000101C`) возвращает адрес недавно
исполненной инструкции. Чтение по SWD не останавливает ядро. Если читать
его часто и асинхронно к ШИМ, доля отсчётов на адресе пропорциональна
времени, проведённому на нём, включая ожидание флеша.

**Сэмплер** — `$D/pcsampler` (исходник в приложении A). Запуск:

```sh
$D/pcsampler/target/release/pcsampler <серийный-ST-Link> <секунд> <блок> <выход.bin>
```

- Подключается через `probe_rs::Session` на 24 МГц SWD. Создание и
  закрытие сессии кратко останавливают ядро, поэтому подключаться и
  отключаться можно только в состоянии Stopped.
- Читает блоками по 64 отсчёта; до и после блока читает `TIM1->CCER`
  (`0x40010020`). Блок помечается «мост активен», если в обоих чтениях
  `CCER & 0x555 != 0`. Бит MOE для этого не годится: он выставлен и в
  Stopped.
- Формат выхода: пары little-endian `u32` — `pc`, `driven`.
- Скорость: 2.7–5.6 тыс. отсчётов в секунду.

**Оркестрация** — `$D/pcprof.py <метка> <рад/с> <секунд>`:

```sh
uv run --no-project python -B $D/pcprof.py base-release-120 120 14
```

Проверяет Stopped, запускает сэмплер (ждёт строку `attached`), затем
`just test-bridge` с планом «velocity на 0.3 с, stop на 0.3+N с»; сэмплер
работает N+9 с и завершается уже после остановки. Запись проверяется так
же, как в 6.4. В этой сессии: 129 344 отсчёта, из них 78 272 при активном
мосте.

**Анализ** (все скрипты в `$D`, читают `<метка>.pcs.bin`):

| Скрипт | Что делает |
|---|---|
| `pcreport.py <метка> <elf>` | символизация уникальных PC через `addr2line -e elf -f -i -C -a`, кэш в `<метка>.frames.json`; сводки по символу линковщика, по внутренней встроенной функции, по файлу, по строке |
| `pctree.py <метка> x <глубина> [подстрока]` | µs за цикл по внешним символам или по цепочкам встраивания внутри заданного символа |
| `pcsub.py <метка> <подстрока-кадра> <глубина> [N]` | отсчёты, в цепочке которых есть кадр; разбивка ниже него и N самых горячих строк |
| `pcinsn.py <метка> <dis.txt>` | доля времени по мнемоникам |
| `pcsite.py <метка> <dis.txt>` | такты за период на адрес по классам инструкций, только символы ISR |
| `pcops.py <метка> <dis.txt> vdiv,vsqrt` | все адреса заданных мнемоник с исходными строками и тактами |

`dis.txt` — `rust-objdump -d --no-show-raw-insn -C firmware.elf`.

Пересчёты: `µs = отсчёты / все_активные × 66.66`,
`такты = отсчёты / все_активные × 11188`.

**Проверка достоверности.**

- Калибровка: медиана по `vdiv` — 14.2 такта, по `vsqrt` — 14.4 (у
  Cortex-M4F оба по 14).
- Сумма по символам ISR — 47.2 µs при 46.3 µs по DWT (разница — вход/выход
  прерывания и учёт после метки).
- Прогноз для `arith.patch` по таблице 4.5 — около 1.0 µs, измерено 0.86.

**Ограничения.**

- Статистика: 1% ISR ≈ 550 отсчётов (±4%); адрес на 10 тактов ≈ 70
  отсчётов (±12%).
- PCSR может отставать на инструкцию; цифры по отдельным инструкциям
  приблизительны, по строкам и функциям — надёжнее.
- «Адресов» в таблице 4.4 — это число различных адресов, не число
  исполнений.
- В выборку входят разгон, установившийся режим и переход к остановке.
- Профиль снят только на +120 (Hall активен, наблюдатель работает в фоне).
  На +450, в удержании тока и в Stopped распределение будет другим.

### 6.7 Грабли

- Не запускать тяжёлые задачи на хосте во время прогона. В одной попытке

## 7. Куда двигаться дальше

Оценки выигрыша — из профиля на +120; после каждого шага нужен A/B.

### 7.1 Сначала ток и запись ШИМ, потом остальное

Сейчас до записи CCR выполняются чтение АЦП, снимки, второй опрос Холла,
команды, deadman, защиты и гейты — по профилю запись происходит примерно
через 24 µs после входа (оценка: сумма блоков до `pwm.set_duties`; момент
записи в этой сессии напрямую не измерялся). Если до записи оставить только
чтение токов, проверку kill-флага, планировщик скорости, гейты и контур
(~14 µs), а команды, защиты и телеметрию перенести после `pwm.set_duties`,
запись сдвинется примерно на 10 µs раньше.

- Среднее время ISR не изменится; вырастет запас до дедлайна ШИМ. Это
  главное условие для 20 кГц и выше (на 20 кГц минимальный запас был
  10–15 µs).
- Команда начнёт действовать на цикл позже.
- Kill-класс ошибок должен по-прежнему отсекать выход в том же цикле:
  перед записью нужна хотя бы проверка флага реестра ошибок.
- Проверять диагностикой `bench-foc-deadline` (метка TIM5 после записи CCR).

### 7.2 Разные частоты и работа по событию

| Что | Сейчас, µs | Идея | Оценка |
|---|---|---|---|
| Опрос `CMD_CHANNEL` | ~1.0 | атомарный флаг «есть команда», в ISR одна загрузка | −0.8 |
| Deadman, staleness, link-гейты | ~0.6 | раз в 1 мс | −0.5 |
| `run_protection` (интеграторы напряжения, температуры, derating) | ~1.0 | 1 кГц с масштабом `dt`; мгновенные проверки тока оставить | −0.8 |
| `hall_fault`, health | ~0.6 | реже или по фронту Холла | −0.4 |
| Копия снимков в `STATE` | 1.2 | каждый N-й цикл или по запросу слушателя | −1.0 |
| Обёртка контура скорости | 1.2 | счётчик циклов вместо `begin_cycle`/`advance` каждый цикл | −0.8 |

Суммарно около −4 µs. Каждое решение меняет семантику защиты или задержку
реакции, поэтому требует согласования (раздел 10).

### 7.3 Один опрос Холла за цикл

`hall::get_snapshot` (`oxifoc-f405/src/control/foc.rs:722`, реализация в
`oxifoc-core/src/foc/hall_embassy.rs:118`) задокументирован как «polled at
low rate», но вызывается каждый цикл и нужен только телеметрии. Он повторяет
начало `sample_for_control`: интервал от фронта, `decayed_velocity`,
`vel_to_erpm`. Варианты: один метод, возвращающий и управляющий отсчёт, и
снимок под одной блокировкой; либо считать снимок только когда кадр
телеметрии действительно нужен. Оценка −1.3 µs. Учесть, что выходы разные:
снимок — интерполяция без ограничителя, управление — с ограничителем
скорости изменения.

### 7.4 Кэшировать решения, которые не меняются внутри цикла

`angle_trustworthy` вызывается три раза за цикл (каждый раз `bl` + `tbb`),
`hfi_active` — дважды, плюс `startup_status`, `is_starting`, `wants_short`.
Вычислять один раз в `PhaseManager::update` и хранить полями. Оценка
−0.5…0.8 µs; заодно убирает четыре таблицы переходов.

### 7.5 Арифметика

- Применить `arith.patch`: −0.86 µs измерено.
- Оставшиеся места из таблицы 4.5: кэши `1/dt`, `1/pll_ki`, `1/period`,
  `1/pole_pairs`, сравнение квадратов вместо `sqrtf` в `controller.rs:870`,
  счётчик вместо `is_multiple_of`. Оценка −0.7 µs.
- Углы в фиксированной точке (u32 «обороты»): `wrap_angle` и
  `angle_difference` вызываются около 30 раз за цикл и занимают 3.2 µs;
  в целых числах заворачивание бесплатное. Оценка −2 µs, но это большая
  переработка оценщиков. Побочная польза: индекс таблицы синуса берётся
  прямо из старших бит.

### 7.6 Телеметрия

- Кадр собирается в ISR с преобразованиями f32 → fixed (5 делений,
  `wrap_angle`). Можно класть в очередь сырые значения, а упаковку делать
  в задаче кодировщика. Оценка −1 µs при включённой записи.
- Измерить ISR без записи — это реальный рабочий режим.

### 7.7 Мелочи

| Что | Оценка |
|---|---|
| Один токен `CriticalSection` на весь ISR (приоритет 0, вытеснять некому) вместо 8 секций | −0.5 µs |
| Прямая запись трёх CCR вместо трёх вызовов `ComplementaryPwm::set_duty` | −0.6 µs |
| Прямое чтение JDR вместо `InjectedAdc::read_latest` | −0.3 µs |
| `hall::now_ticks` (расширение до u64) | до −0.3 µs |
| `foc_telem.unwrap_or_default()` — копирование `FocOutput` | −0.2 µs |

### 7.8 Ориентир по сумме

7.2 (−4) + 7.3 (−1.3) + 7.4 (−0.6) + 7.5 без фиксированной точки (−1.5) +
7.6 (−1) + 7.7 (−1.5) ≈ −10 µs, то есть около 36 µs. Фиксированная точка
и меры из раздела 8 — сверх этого.

## 8. Промахи кэша флеша

### 8.1 Механизм

На 168 МГц флеш F405 работает с 5 wait states. ART-ускоритель скрывает
задержку для последовательного кода (prefetch), а для переходов держит кэш
на 64 строки по 128 бит; для литеральных пулов — кэш данных на 8 строк
(по RM0090; стоит перепроверить по текущей редакции). Последствия:

- невыполненный условный переход бесплатен (код идёт подряд);
- выполненный переход на адрес вне кэша ждёт чтения флеша — в профиле такие
  переходы стоят 9–15 тактов вместо 2–3;
- загрузка константы из литерального пула при промахе стоит до 16 тактов;
- `tbb`/`tbh` платят дважды: чтение таблицы и сам переход.

ISR за цикл проходит ~400 различных мест переходов и ~1000 строк флеша —
кэш на 64 строки переполняется многократно, и к следующему циклу в нём
остаётся только хвост предыдущего.

### 8.2 Что пробовать, по убыванию ожидаемой пользы

1. **Меньше кода за цикл** (раздел 7.2–7.4). Эффект нелинейный: чем
   меньше различных целей переходов, тем выше доля попаданий у оставшихся.
2. **Раскладка «горячее подряд».** Горячий путь должен идти без
   выполненных переходов, холодный код — вынесен:
   - `#[cold] #[inline(never)]` на редкие ветви: обработчики команд,
     аварийные пути, блоки с `defmt`, возбуждение детекции внутри
     `run_foc_cycle` (функция 26 КБ, почти вся холодная);
   - `core::hint::cold_path()` / `likely` там, где ветвь мелкая;
   - разделить `run_foc_cycle` на короткую горячую часть и холодную
     `slow_path`.
   Метрика успеха — число мест переходов дороже 4 тактов в `pcsite.py`
   (сейчас 148) и их сумма (795 тактов сверх нормы).
3. **Выравнивание целей переходов на 16 байт.** При промахе читается
   128-битная строка; если цель в конце строки, полезных байт мало и сразу
   нужен второй доступ. Флаги-кандидаты:
   `-C llvm-args=--align-all-nofallthru-blocks=4`,
   `-C llvm-args=--align-all-functions=4`. Не проверялось; эксперимент
   дешёвый (только флаг и один A/B).
4. **PGO по отсчётам PC.** LLVM умеет раскладывать блоки по sample-профилю
   (`-Zprofile-sample-use`, `-Zdebug-info-for-profiling`). Отсчёты PCSR
   можно сконвертировать в текстовый формат sample-профиля. Работает ли
   это для `thumbv7em` и даёт ли разделение функций — неизвестно;
   исследовательская задача.
5. **Исполнение из ОЗУ, повторно.** Прошлый опыт (`ram-foc`) дал +10.7% на
   168 МГц, но:
   - в ОЗУ были только `ADC`, `run_foc_cycle`,
     `update_phase_with_applied_voltage`, `step_with_injection`; по профилю
     ещё ~11 µs кода оставалось во флеше
     (`step_current_control_with_feedback`, `blend_with_observer`,
     `grant_torque`, `step_scheduled_velocity`, `set_duty`,
     `angle_trustworthy`, `space_vector_pwm`), а вызовы между флешем и ОЗУ
     идут через veneer;
   - код из `0x2000_0000` выбирается по системной шине, что медленнее
     I-Code.
   Варианты: (а) перенести весь горячий набор по списку из 4.1 и проверить
   veneer'ы по map-файлу; (б) ремап SRAM на адрес 0 (`SYSCFG_MEMRMP`),
   чтобы выборка шла по I-/D-Code — в заметке
   [f405-clock-memory-bench](f405-clock-memory-bench-2026-11-10.md) это
   прямо названо непроверенным. Для (б) нужно сначала убедиться по RM0090,
   что при ремапе I-шина действительно достаёт до SRAM1, и перенести VTOR.
   CCM на F405 — только данные, код там исполнять нельзя.
6. **Таблицы переходов — точечно.** Глобальное отключение хуже (+0.6 µs).
   Убирать конкретные горячие `match` (таблица 4.6) кэшированием результата.
7. **Литералы — низкий приоритет.** Глобальный `+execute-only` хуже
   (+0.45 µs). Учесть обратный эффект: каждая новая константа-обратное
   значение добавляет литерал.

## 9. Выброс 91 µs: логирование в ISR

В отбракованной попытке `arith-minimal-0-450-1` (хост задержал affirm на
237 мс) самый длинный цикл занял 91.03 µs при периоде 66.66 µs. По записи
он пришёлся на t≈4.2456 с, за 89 мс до снятия ШИМ (сопоставление по `seq`
по модулю 2^16); в следующие десятки миллисекунд скорость начала падать. В логе в этот момент три сообщения из ISR:
`CommTimeout raised: …`, `failsafe: stopping-class fault active`,
`stop sequence armed: policy=… seed_iq=…`.

Вероятная причина — три `defmt::warn!` в одном цикле ISR. Отдельным A/B
это не изолировано. Похоже на выбросы 88–94 µs из прошлых заметок с
пометкой «cause unconfirmed». Что сделать:

- подтвердить: вызвать `CommTimeout` намеренно (прекратить affirm) на
  образе с `bench-cycle-outliers` и посмотреть секции самого длинного цикла;
- исправить: в ISR ставить флаг/код события, сообщение печатать из задачи;
- проверить другие длинные редкие пути: применение конфигурации внутри
  обработки команд (`apply_phase_source`, `apply_hall_tuning`,
  `from_config_clamped`, `memcpy`), `SW overcurrent FAULT`, `FOC step error`.

## 10. Открытые вопросы

1. **Что оптимизируем?** Среднее время тела, запас до записи ШИМ, загрузку
   CPU или худший случай — это разные задачи. На 15 кГц ISR занимает ~71%
   CPU, свободно ~21%. На 20 кГц тот же ISR — около 93%, отсюда пропуски
   ACK в инструментированных сборках. Нужна целевая частота ШИМ и
   требуемый запас.
2. **Что обязано выполняться каждый цикл?** Интеграторы напряжения,
   температурные пороги, deadman, link-гейты, health Холла. Какая задержка
   реакции допустима для каждого.
3. **Допустимая задержка команд.** Опрос по флагу её не добавляет; перенос
   обработки после записи ШИМ добавляет один цикл.
4. **Семантика угла Холла в телеметрии.** Нужна ли именно интерполяция без
   ограничителя, или годится управляющий отсчёт.
5. **Политика бит-точности.** Часть тестов сравнивает побитно с эталоном.
   Замена деления умножением на обратное меняет результат на ≤1 ulp.
   Рекомендация автора этого документа (решение за владельцем):
   - побитное сравнение с замороженной копией старого кода (`legacy_grant`
     в `torque_grant_tests.rs`) — леса от рефакторинга `b9337f4`; блокировать
     арифметические правки оно не должно. Перевести на допуск в несколько
     ulp или убрать копию;
   - сохранить побитное равенство прямого и переиспользуемого путей
     (`grant_torque` == `grant_torque_constrained`). Оно функционально
     значимо: `ActuatorFeedback::record`
     (`motor/foc_driver/velocity_schedule.rs:93`) вызывает
     `note_clip(requested - granted)`, а там проверка знака — разница в
     1 ulp уже выставляет флаг блокировки контура скорости;
   - следствие: границы шины оба пути должны считать одной функцией. Замена
     на `1/mod_q` это сохраняет; вариант «не делить, пока лимит не сработал»
     только в прямом пути — нарушает.
   Для кодека телеметрии — проверить границы квантов.
6. **Наблюдатель в фоне.** Ниже blend_low он не влияет на выход, но стоит
   ~4 µs. Можно ли считать его реже или упростить вне зоны смешивания, не
   ухудшив готовность к передаче управления.
7. **Профили других режимов.** +450 (наблюдатель активен), удержание тока,
   Stopped, работа под нагрузкой. Все замеры — без нагрузки.
8. **G474.** `oxifoc-core` общий; любые правки нужно измерять и там. У G4
   CCM-SRAM исполняемая, есть CORDIC — выводы про флеш и RAM для F405 туда
   не переносятся.
9. **Исполнение из ОЗУ и ремап** (раздел 8.2, п. 5) — проверить по
   документации до эксперимента.
10. **Выравнивание и sample-PGO** (раздел 8.2, пп. 3–4) — работают ли
    флаги на этом тулчейне.
11. **Пролог/эпилог: 3 µs.** Крупные функции сохраняют `d8–d15`. Стоит ли
    менять границы встраивания — неясно; нужен эксперимент.
12. **Упрощение `detection_timing`** через `CMD_CHANNEL` (раздел 5).
13. **Стоимость самой записи телеметрии**: сколько занимает ISR без неё.

## Приложение A. Исходник сэмплера

`$D/pcsampler/Cargo.toml`: зависимости `probe-rs = "0.32"`, `anyhow = "1"`,
пустая секция `[workspace]`. Сборка: `cargo +stable build --release`.

```rust
//! Non-intrusive DWT_PCSR sampler. Attach while the controller is Stopped.
use anyhow::{bail, Context, Result};
use probe_rs::{probe::list::Lister, MemoryInterface, Permissions};
use std::io::Write;
use std::time::{Duration, Instant};

const DWT_PCSR: u64 = 0xE000_101C;
const TIM1_CCER: u64 = 0x4001_0020;
const DHCSR: u64 = 0xE000_EDF0;

fn main() -> Result<()> {
    let args: Vec<String> = std::env::args().collect();
    if args.len() != 5 {
        bail!("usage: pcsampler SERIAL SECONDS BLOCK OUT");
    }
    let seconds: f64 = args[2].parse()?;
    let block: usize = args[3].parse()?;
    let probes = Lister::new().list_all();
    let info = probes
        .iter()
        .find(|p| p.serial_number.as_deref() == Some(args[1].as_str()))
        .context("probe not found")?;
    let mut probe = info.open()?;
    probe.set_speed(24_000)?;
    let mut session = probe.attach("STM32F405RGTx", Permissions::default())?;
    let mut core = session.core(0)?;
    if core.read_word_32(DHCSR)? & (1 << 17) != 0 {
        bail!("core halted");
    }
    eprintln!("attached");
    let mut out = std::io::BufWriter::new(std::fs::File::create(&args[4])?);
    let start = Instant::now();
    let limit = Duration::from_secs_f64(seconds);
    let (mut total, mut active) = (0u64, 0u64);
    let mut buf = vec![0u32; block];
    while start.elapsed() < limit {
        let before = core.read_word_32(TIM1_CCER)?;
        for slot in buf.iter_mut() {
            *slot = core.read_word_32(DWT_PCSR)?;
        }
        let after = core.read_word_32(TIM1_CCER)?;
        // Phase channel enables, not MOE: MOE stays set while Stopped.
        let driven = (before & 0x555 != 0 && after & 0x555 != 0) as u32;
        for pc in &buf {
            out.write_all(&pc.to_le_bytes())?;
            out.write_all(&driven.to_le_bytes())?;
        }
        total += block as u64;
        active += u64::from(driven) * block as u64;
    }
    out.flush()?;
    let dt = start.elapsed().as_secs_f64();
    eprintln!("samples={total} driven={active} rate={:.0}/s", total as f64 / dt);
    Ok(())
}
```

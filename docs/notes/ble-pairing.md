# BLE pairing for the skateboard

The C5 is the BLE peripheral for the remote and the host app. Both are
centrals. A trusted laptop or phone can manage enrollment and configure the
board. The selected remote controls traction and braking. Service commands
that can drive the motor or start detection require an explicit service mode
with the board stopped. This design targets accidental pairing and unauthorized
control by nearby devices. The commissioning procedure assumes physical access
to the equipment at home.

## First setup

- Enroll the first administrator through a local setup path while the C5 is
  accessible on the bench. The administrator can enroll a phone using LE Secure
  Connections Passkey Entry and the phone's system dialog.
- Keep enrollment closed during normal operation. Enrollment requires a stopped
  controller with drive inhibited and expires after a short window.
- Persist BLE bonds and their roles on C5. Admit Ergot traffic only after the
  device has authenticated using the enrolled bond. BLE addresses help find a
  peer. The stored bond establishes its identity.
- Keep an optional physical recovery path in mind before sealing the enclosure.
  A QR code held privately in a password manager or backed-up encrypted storage
  could support recovery later. It represents a unique board secret, with
  proof of possession if used over BLE. Ordinary enrollment uses the trusted
  administrator, so recovery QR support can wait.

## Add or replace a remote

1. In OxiFOC Host, connect to the board using an administrator bond and choose
   **Add remote**. C5 opens a short enrollment window while the board is stopped
   and drive is inhibited. If an old remote is connected, C5 frees its connection
   slot for the candidate and keeps its bond and selection.
2. Put the new remote into pairing mode with its button. The remote connects
   directly to C5 and displays the fresh six-digit passkey generated by Trouble,
   including any leading zeros.
3. Enter the displayed code in OxiFOC Host. Host sends it over the existing
   authenticated connection to C5, scoped to the current pairing attempt. C5
   supplies it to Trouble for the candidate connection. A wrong code,
   cancellation or timeout ends the attempt and clears the passkey.
4. Both devices save the authenticated bond. C5 verifies that the new remote
   can reconnect using it. The administrator then selects it as the sole drive
   controller and can revoke the old bond. If enrollment fails or is cancelled,
   the previously selected remote can reconnect and resume normal operation.

Use LE Secure Connections Passkey Entry for this flow. The remote is the BLE
central with `DisplayOnly` capabilities. C5 is the peripheral with
`KeyboardOnly` capabilities during remote enrollment and takes input from
the administrator session. In Trouble, the remote displays `PassKeyDisplay`
and C5 handles `PassKeyInput` with `pass_key_input`. Require an authenticated
bond before granting the remote an enrolled role.
[Bluetooth Core Specification, Security Manager, Table 2.8](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v6.3/out/en/host/security-manager-specification.html)

The same flow works in the phone app and on a laptop with a command such as
`pair remote`. A replacement remote needs a display and the BLE profile.
The board can stay inside its enclosure. USB enrollment is deferred.

## Runtime and validation

The current bridge supports one BLE connection and the remote currently uses a
fixed bridge address. Enrollment needs the administrator and candidate remote
connected concurrently. Let a new remote discover boards with an open
enrollment window and remember the enrolled board through its bond. Enable
Trouble's `security` feature on C5 and the remote. In normal use, reserve
capacity for the selected remote while the phone is connected. Evaluate the
C5 controller's accept list with private phone addresses. Check authorization
before forwarding traffic and keep the STM32 command watchdog independent
of BLE connection state.

Start with a laptop administrator and one selected remote. Verify screen-based
enrollment, wrong-code rejection, cancellation, timeout, bond persistence across
reboot and recovery of the previous remote after an unsuccessful replacement.
Then verify Android enrollment, revocation, simultaneous phone telemetry and
remote control, and loss of the remote link. Reconnection requires neutral
followed by fresh driver intent. See the [remote design](remote-design.md) and
[drive watchdog](../safety.md).
